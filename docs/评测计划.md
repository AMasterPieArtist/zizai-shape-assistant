# 下一轮评测计划（待执行）

目标是验证推荐是否可用、用户是否能完成任务。自动测试不能替代这一轮。计划规模为 **4 类画像 × 5 个场景，共 20 组**，不属于已完成结果。

| 画像 | 应固定的差异 |
| --- | --- |
| 食堂为主 | 食堂来源、正常工作节奏 |
| 外卖为主 | 外卖来源、准备时间少 |
| 经常加班 | 工作繁忙、经常晚睡、已有游泳与步行安排 |
| 明确忌口 | 使用系统支持的具体忌口标签，检查全部候选与替换 |

| 场景 | 观察与验收重点 |
| --- | --- |
| 首次生成计划 | 来源、偏好与时间限制是否体现；理由是否有依据 |
| 连续换三批 | ID、品类与搭配是否有实质变化；候选不足时是否如实提示 |
| 搜索并自选、外卖采纳 | 找得到目标品类；仅采纳后保存，刷新一致 |
| 取消下午茶 | 总量正确联动，其他餐次、小食与运动保留 |
| 加班调整晚餐并取消游泳 | 草案前后差异正确，确认前不变、确认后步行保留 |

## 记录方法

当前数据库只有一份活动画像。计划与调整有快照，但没有完整的 20 组评测档案或每一步界面回放。**不要等所有画像测完后仅凭数据库补写结果。**

每个画像用一份独立测试数据库，避免覆盖日常数据。在项目根目录另开终端，例如：

```powershell
python app.py --port 8770 --db data/evaluation/canteen.sqlite3
```

浏览器使用 `http://127.0.0.1:8770`。换下一类画像时停止该测试服务，换另一个数据库名，如 `delivery.sqlite3`，再启动。评测数据库默认被 `.gitignore` 排除。

每完成一个场景，立即记录：测试编号、画像、用户要求、结果摘要、是否通过、具体问题、截图路径、修复优先级。对结果满意与否、人是否看懂等主观判断，需要人工记录；事件与调整历史可作为证据补充。截图与记录采用合成资料，避免公开真实个人信息。

建议编号 `C01-S01` 至 `C04-S05`；每条记录用如下模板：

```text
编号：
日期 / 应用、Prompt、知识库版本：
画像与模式：
用户要求：
预期行为：
实际结果 / 调整 ID 或计划版本：
是否通过 / 具体问题：
问题类型：数据 / 推荐 / 交互 / 保存
截图：
修复优先级：
```

完成后汇总任务通过数、重复候选比例、问题分布与典型失败例；优先修复阻断使用与忌口错误。随后邀请 3–5 位接近目标用户的人试用，观察任务完成、决策时间与采纳意愿。小样本只能发现问题，不能据此证明长期效果或市场需求。
